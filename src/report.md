# Отчет по нагрузочному тестированию

## 1. Гипотеза и ожидаемое поведение
Предполагается, что узким местом системы являются операции чтения. Для оптимизации применена балансировка трафика и репликация базы данных. 
**Целевые показатели:** 
* Отсутствие ошибок HTTP 5xx при конкурентной нагрузке.
* Время ответа (p95 latency) не более 100 мс.
* Строгое распределение запросов на чтение (GET) в пропорции 2:1:1 между master-узлом и двумя read-узлами.
* Строгая маршрутизация запросов на запись (POST/PUT/DELETE) исключительно на master-узел.

## 2. Конфигурация стенда
* **СУБД:** PostgreSQL (bitnami) в режиме Primary-Replica (1 мастер, 1 реплика).
* **Backend:** 3 экземпляра API. Основной (`api-ppo`) подключен к Primary-БД. Два дополнительных (`api-ppo-read1`, `api-ppo-read2`) подключены к Replica-БД. В дополнительных экземплярах отключено применение миграций.
* **Балансировщик:** NGINX. Разделение трафика реализовано через директиву `map` по HTTP-методу.
* **Мониторинг:** Prometheus (метрики), Promtail + Loki (логи), Grafana (визуализация).

## 3. Сценарий и объем нагрузки
Тестирование проводилось инструментом `k6`.
* **Авторизация:** выполняется однократно в функции `setup`, полученный JWT передается виртуальным пользователям.
* **Сценарий:** каждый пользователь в цикле выполняет один GET-запрос (`/api/v2/systems`) и один POST-запрос (`/api/v2/systems`).
* **Объем нагрузки:** 30 одновременных виртуальных пользователей.
* **Профиль:** разгон до 30 VUs за 10с, удержание нагрузки 30с, плавная остановка 10с. Общая длительность теста — 50 секунд.

## 4. Полученные метрики
По результатам прогона скрипта `loadtest.js` зафиксированы следующие показатели:
* **Общее число HTTP-запросов:** 2397
* **Пропускная способность:** ~46.6 req/s
* **Процент ошибок:** 0.00%
* **Среднее время ответа:** 10.44 ms
* **Время ответа 95-го перцентиля:** 20.08 ms

На основе статистики Loki в Grafana зафиксировано:
* GET-запросы распределились на 3 контейнера в пропорции 50% / 25% / 25%.
* POST-запросы на 100% обработаны контейнером `api-ppo`.

## 5. Выводы
Заданная конфигурация инфраструктуры работает корректно. NGINX успешно маршрутизирует операции модификации данных на master-узел, исключая ошибки записи в read-only реплики. Балансировка операций чтения выполняется согласно заданным весам (2:1:1). 
Задержка репликации базы данных не повлияла на консистентность в рамках заложенного тестового сценария. Целевые показатели производительности (p95 < 100ms) достигнуты с большим запасом (20.08 ms). Инфраструктура готова к дальнейшему масштабированию.
